# Costa Rican electronic invoice reception

The server-side `@vetx/fiscal-cr` adapter transmits already signed XML and queries the tax authority by its 50-digit document key. A successful HTTP intake returns `submitted`. The application must poll for a subsequent tax-authority decision. A final response can include signed receipt XML, which should be retained for verification and reconciliation. See Hacienda’s [reception API](https://www.hacienda.go.cr/docs/ComprobantesElectronicosAPI.html) and [authentication guide](https://www.hacienda.go.cr/docs/Guia_IdP.pdf).

Configure `HACIENDA_TOKEN_URL`, `HACIENDA_RECEPTION_URL` (the collection for POST), `HACIENDA_CLIENT_ID`, `HACIENDA_HTTP_TIMEOUT_MS` and `HACIENDA_RESPONSE_BYTES` for the selected environment. Load each issuer’s API username and password from its secret-manager reference. Construct one client per issuer and environment. The client authenticates over HTTPS, reuses its expiring token, bounds incoming response sizes and prevents credential forwarding via redirects.

Persist the exact signed XML and original key before delivery. After an uncertain send, check that key. A positive lookup reconciles the existing submission. A missing document following a transport failure remains unconfirmed and may be retried with the same key and signed bytes. A documented HTTP 400 also prompts a status lookup because Hacienda uses that code for duplicates. Store a known final decision and its signed response separately from intake and payment status. Consult the [official schema index](https://atv.hacienda.go.cr/ATV/ComprobanteElectronico/frmAnexosyEstructuras.aspx) for the document format.

The invoice builder accepts a frozen sale snapshot with issuer and recipient details, the issuer's registered economic activity, the software provider's taxpayer ID, branch and terminal sequence, and explicit tax and product classifications. It supports ordinary domestic, VAT-taxed invoice lines and reconciles each amount with the recorded checkout. Exemptions, exonerations and other document kinds need their own supported profiles. The issuer or invoicing provider supplies its production configuration when it enables the integration.

The worker must have OpenSSL-compatible issuer material, a trusted signature policy and the `xmllint` executable from libxml2. The signing adapter creates an enveloped XAdES signature, and `prepareFiscalInvoice` validates the signed bytes locally against the [official April 2026 v4.4 invoice schema](https://www.hacienda.go.cr/docs/FacturaElectronica_V4.4.xsd) and its [W3C XML Signature schema](https://www.w3.org/TR/xmldsig-core/xmldsig-core-schema.xsd). The upstream SHA-256 digests are `926ba81325bc21102755bd8e4e570a63caaca086e680a877c3a6d15d6ee8a62f` and `d102ad3df7664c307e0c2c776ba4a90513b1969974d8a940bae1a77f9f21e15d`. Offline validation and loopback reception tests use disposable certificates. Government sandbox acceptance remains unverified.
